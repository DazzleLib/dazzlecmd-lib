# Human Test Checklist: safedel and links whose target is gone; safedel on dazzle-filekit

**Target version:** dazzlecmd-lib 0.10.42-alpha to 0.10.46-alpha (used through dazzlecmd 0.12.29's `dz safedel`)
**Ships with commits:** `f300e6e` (0.10.42), `d2a681b` (0.10.43), `b10b8d8` (0.10.44), `562126a` (0.10.45), `f3ff5a8` (0.10.46), `c5caf55` (test)
**Companion automated tests:** 46 tests in `tests/test_core_safedel_broken_links.py` (2), `tests/test_core_safedel_alt_path.py` (25), `tests/test_core_safedel_writer_version.py` (2), `tests/test_core_safedel_linkinfo.py` (13), `tests/test_core_safedel_streams.py` (4). Full suite: 834 passed, 2 skipped on Windows; 825 passed, 10 skipped under WSL.

## What this is

A hand-run check of what changed in safedel across these five versions, for a person at a real Windows terminal:

1. a deleted symlink whose target does not exist can be recovered (it could not before);
2. a junction whose target folder is gone is recognised as a junction, deleted as one, and recovered as one;
3. link detection, the other-runtime path in the manifest, and NTFS stream detection now come from dazzle-filekit, with no visible change;
4. each manifest records the version that wrote it.

Everything you delete is created for the purpose in a throwaway folder. **The batches do land in your real trash store**, because safedel always uses the per-drive store for a file on a local drive (`C:\Users\<you>\.safedel-trash` for anything on C:), and no command-line setting changes that (`SAFEDEL_STORE` moves only the fallback store). Each step recovers what it deletes, so the store is left as it was; a leftover batch holds only throwaway test files.

## Prerequisites

1. Windows 10/11, `dz` on PATH (dazzlecmd 0.12.29), dazzlecmd-lib 0.10.46 or later installed (`python -c "import dazzlecmd_lib; print(dazzlecmd_lib.__version__)"`).
2. Creating a symlink needs Developer Mode or an elevated shell. Junctions need neither. If you cannot create symlinks, skip HV.1 and 1.1.
3. A throwaway folder. Every step below runs from inside it, and every path you hand to `dz safedel` is a name you created in it.

   **cmd.exe**:
   ```cmd
   mkdir %TEMP%\sd-check && cd /d %TEMP%\sd-check
   ```

   **PowerShell**:
   ```powershell
   New-Item -ItemType Directory -Force "$env:TEMP\sd-check" | Out-Null; Set-Location "$env:TEMP\sd-check"
   ```

   **POSIX (Git Bash)**:
   ```bash
   mkdir -p "$TEMP/sd-check" && cd "$TEMP/sd-check"
   ```

4. Use `dz safedel recover last` only right after your own delete: if another tool deleted something in between, "last" is theirs. When in doubt, recover by the batch name the delete printed (`To recover:  dz safedel recover <name>`).

## High-Value Verification (~5 minutes)

### HV.1 -- A broken symlink comes back

Validates: recovery of a `broken_link` entry (0.10.42).

- [ ] **Steps** (cmd.exe; PowerShell and bash in 1.1):
  1. `mklink dangling.txt never-existed.txt`
  2. `dz safedel --yes dangling.txt` (last line: `safedel: STAGED 1`)
  3. `dz safedel recover last`
  4. `dir dangling.txt`
- [ ] **Expected:** step 3 prints `Recovered symlink: ...dangling.txt -> never-existed.txt` and exits 0; step 4 lists `dangling.txt` as `<SYMLINK>` pointing at `never-existed.txt`.
- [ ] **Why this matters:** before 0.10.42 step 3 said "No content available to recover" and the link was gone for good.

### HV.2 -- A junction to a deleted folder is deleted and recovered as a junction

Validates: detection from the link itself, and recreation with a missing target (0.10.42).

- [ ] **Steps** (cmd.exe):
  1. `mkdir target` then `mklink /J jn target` then `rmdir target`
  2. `dz safedel --dry-run jn`
  3. `dz safedel --yes jn`
  4. `dz safedel recover last`
  5. `dir`
- [ ] **Expected:** step 2 shows `kind:  junction -> ...\target` (not an unknown type, not a folder); step 4 prints `NOTE: the junction's target does not exist: ...\target`; step 5 lists `jn` as `<JUNCTION>` with `[...\target]`.
- [ ] **Why this matters:** before 0.10.42 the junction was classified as an unknown file type, and recovery failed in PowerShell's `New-Item`.

### HV.3 -- An ordinary junction still says "the target is not touched"

Validates: the switch to filekit's link detection (0.10.45) changed nothing visible.

- [ ] **Steps:** `mkdir t2` and put a file in it (`echo keep > t2\k.txt`), `mklink /J j2 t2`, then `dz safedel --yes j2`.
- [ ] **Expected:** the preview says `remove the link only; what it points at is not touched`; afterwards `t2\k.txt` still exists.
- [ ] **Why this matters:** link detection is the first thing safedel's safety rules depend on.

### HV.4 -- The manifest names the version that wrote it

- [ ] **Steps:** `echo x > v.txt`, `dz safedel --yes v.txt`, note the batch name it prints, open `%USERPROFILE%\.safedel-trash\<batch name>\manifest.json` (read only), then `dz safedel recover <batch name>`.
- [ ] **Expected:** `"safedel_version": "0.10.46-alpha"` (or later), not `"0.1.0"`; `"original_path_alt"` is the `/mnt/<drive>/...` form of `"original_path"`.

## Section 1: details

### 1.1 Broken symlink in other shells

- [ ] **PowerShell**: `New-Item -ItemType SymbolicLink -Path dangling2.txt -Target never2.txt`, then steps 2 to 4 of HV.1 with `Get-Item dangling2.txt | Format-List LinkType,Target`.
- [ ] **POSIX (Git Bash, with `MSYS=winsymlinks:nativestrict`)**: `ln -s never3.txt dangling3.txt`, then `dz safedel --yes dangling3.txt`, `dz safedel recover last`, `ls -l dangling3.txt`.
- [ ] **Expected:** the link returns pointing at the same name in each shell.

### 1.2 A broken directory symlink

- [ ] **Steps** (cmd.exe): `mklink /D dlink never-a-folder`, `dz safedel --yes dlink`, `dz safedel recover last`, `dir`.
- [ ] **Expected:** `dlink` returns as `<SYMLINKD>`. If it returns as a file symlink, report it: the manifest recorded the wrong kind.

### 1.3 Recovering onto an occupied path is refused

- [ ] **Steps:** repeat HV.2 up to step 3, then `mkdir jn` (something now sits where the junction was), then `dz safedel recover last`.
- [ ] **Expected:** recovery refuses for that item and names the occupied path; the folder you created is untouched. (Not changed by these versions; checked because the recreation path changed.)

### 1.4 A file with an alternate data stream

- [ ] **Steps** (cmd.exe): `echo main > s.txt`, `echo hidden > s.txt:notes`, `dz safedel --dry-run s.txt`.
- [ ] **Expected:** the same stream warning as before 0.10.46 naming `:notes:$DATA`; no warning for a file downloaded from a browser that has only `Zone.Identifier`.

## What the automated tests DON'T cover

- The real `dz safedel` command's output wording at a terminal (the tests call the engine).
- Symlinks created by `mklink` from cmd.exe and by Git Bash's `ln -s` (the tests use `os.symlink`).
- Codepage rendering of the `->` arrows and paths with non-ASCII characters.
- A real browser-downloaded file's `Zone.Identifier`.
- Junctions on a second drive, and a broken link whose target was on another drive.

## Reporting issues found

Note the step, copy the exact command and output, note the batch name (do not recover it, so its manifest can be read), and file an issue on DazzleLib/dazzlecmd-lib naming this checklist and the version.

## Cleanup

1. `dz safedel list today` and recover any batch from this run that is still there (by its name), or leave it: it holds only files from `sd-check`.
2. Step out of the folder (`cd %TEMP%`), then remove it with your file manager or `dz safedel --yes "%TEMP%\sd-check"`. It contains a junction and links: safedel removes those as links and does not follow them.
